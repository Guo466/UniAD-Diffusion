## 1. 计算几何专题一：Douglas-Peucker 多边形简化算法

**对应 PR**：04-24 障碍物约束与代价函数生成器

### 1.1 问题背景

障碍物多边形通常由感知/预测模块给出，可能包含大量冗余顶点（比如激光雷达轮廓拟合出的密集点云边界）。直接用这些顶点构造约束/代价，会导致：
- 折线段数量多 → `SmoothPolyline` 的 `LogSumExp` 融合要对更多线段求距离，计算量线性增长；
- 冗余共线点对几何形状没有贡献，纯粹浪费计算资源。

### 1.2 算法原理

Douglas-Peucker（道格拉斯-普克）算法是经典的**多边形/折线简化**算法，核心思想是**分治 + 最大偏差点检测**：

1. 连接折线的起点和终点，形成一条基准直线。
2. 计算折线上所有中间点到这条基准直线的**垂直距离**，找到距离最大的点 $P_{max}$。
3. 如果 $P_{max}$ 的距离小于阈值 $\epsilon$（本项目中障碍物简化精度取 `0.05m`），则认为起点-终点这条直线足以近似整段折线，中间所有点全部丢弃。
4. 否则，保留 $P_{max}$，以它为界把折线切成两段（起点→$P_{max}$，$P_{max}$→终点），分别递归执行步骤 1-3。
5. 递归终止后，所有被保留下来的点（包括起点、终点和各级递归中的 $P_{max}$）组成简化后的折线。

**直觉理解**：算法只保留"对形状贡献最大"的拐点，把近似共线的中间点都丢弃，阈值 $\epsilon$ 越大简化程度越高（丢的点越多），阈值越小则越贴近原始形状。

### 1.3 复杂度

- 平均情况：$O(n\log n)$（类似快速排序的分治过程）。
- 最坏情况（每次只能切掉一个点，比如螺旋状折线）：$O(n^2)$。
- 对于障碍物多边形这种点数通常不多（几十到几百个点）的场景，性能完全够用。

### 1.4 与本项目的连接

Douglas-Peucker 简化在 `clothoid_path_optimizer` 里被两次使用：
1. **04-24 PR**：对障碍物多边形做精度 `0.05m` 的抽稀，降低后续约束/代价生成的计算量。
2. **07-14/07-15 PR**：`BuildAndSimplifyBoxCollisionPolyline`/`BuildAndSimplifyRestrictionPolyline` 在采样生成 box_collision/restriction 折线后，同样做 Douglas-Peucker 抽稀——但这也正是 07-14/07-15 PR 修复的问题根源之一：抽稀会把一些"看似冗余"但导致下游 `ShiftPolyline`/`SmoothPolyline` 处理异常的尖锐拐角保留下来（因为拐角点的偏差本来就很大，Douglas-Peucker 不会误删它），所以 `ChamferAcuteAnglesOnPolyline` 必须放在 Douglas-Peucker **之前**调用，先把尖锐拐角磨平，再抽稀，顺序不能颠倒。

## 2. 计算几何专题二：折线法向偏移的两种算法（角平分线法 vs 射线求交栈式合并法）

**对应 PR**：07-14/07-15 ShiftPolyline 重构

### 2.1 问题的数学本质

给定一条折线 $\{p_0, p_1, \ldots, p_n\}$，要生成一条**整体沿法向偏移距离 $d$** 的新折线（比如把车道中心线偏移出车道边界）。

### 2.2 方法一：角平分线法（原实现，有缺陷）

对折线上每个内部顶点 $p_i$（$0<i<n$），计算它左右两条邻边的**角平分线方向**，沿角平分线方向移动一个"修正后的偏移量" $d_i' = d/\cos(\theta_i/2)$（$\theta_i$ 是夹角的一半，这个修正保证偏移后两条邻边仍然精确保持偏移距离 $d$）。

**缺陷**：当夹角 $\theta_i$ 很小（拐角非常尖锐）且 $d$ 较大时，$d_i' = d/\cos(\theta_i/2)$ 会变得非常大，导致偏移后该顶点两侧的线段长度变得比原线段长度还长，甚至**超过临界值使线段发生方向翻转**（原线段的起点在终点之前，偏移后箭头方向反了）。原实现检测到这种翻转后，直接**放弃整体偏移、返回原折线**——这是一种"一票否决"式的粗暴处理，导致仿真里出现"偏移折线与原折线完全重合"的诡异现象。

### 2.3 方法二：射线求交 + 栈式回退合并法（重构后）

这是计算几何里处理"多边形/折线整体偏移（offsetting）"问题的**经典算法**（可以类比 Minkowski 和/多边形 buffer 算法中处理"内缩自交"问题的思路），核心步骤：

1. **构造偏移射线**：对折线的每一条原始线段，计算它整体沿法向偏移 $d$ 后得到的新线段所在的**有向直线**（`DirectedLine`，包含方向信息，不仅仅是几何直线）。
2. **用栈维护"已确定保留"的偏移线段**：
   - 依次处理每条偏移直线，尝试与栈顶的直线求交点；
   - 如果交点相对**栈顶那条线段的方向**发生了"翻转"（即交点落在了栈顶线段被期望的起点之前——意味着栈顶线段在当前偏移量下已经被后面的线段"吃掉"/覆盖了），说明栈顶线段在几何上已经不该存在了，**弹出栈顶**，继续和新的栈顶求交，直到求出一个不翻转的交点，或者栈为空；
   - 找到有效交点后，压入当前线段（连同刚求出的交点作为它的新起点）。
3. **收尾**：处理完所有线段后，栈中剩余的线段序列，依次取相邻线段的交点（加上最后一段的终点），拼成最终的偏移折线。

**为什么这个算法能处理"连续多个拐角级联翻转"？** 因为使用栈结构，一旦发现某条线段被新线段"吃掉"，就会继续向前（向栈底方向）比较，直到找到一条真正不受影响的线段为止——这天然地支持了"多个连续尖锐拐角在大偏移量下连锁失效"的场景（比如三个连续的尖角，大偏移下前两个都被第三个"吞并"），而角平分线法完全没有能力处理这种级联情况。

### 2.4 代码实现要点回顾

- 单测覆盖的边界场景（复习时应能口述）：
  - 单个拐角翻转 → 退化为一个交点（原本两条线段变成一条）；
  - 连续多个拐角翻转 → 级联收敛到同一个交点；
  - 偏移距离小于临界值 → 行为与原算法一致（不应该有回归）；
  - 共线/近似共线（夹角趋近 0°）→ 不应产生 NaN/Inf（除以 $\sin(\theta)$ 或 $\cos(\theta/2)$ 这类操作在角度趋近 0 或 180° 时容易除零，需要特殊判断或钳制）。

### 2.5 面试可能会问的追问

**Q：为什么不直接用现成的多边形 buffer 库（比如 Clipper/Boost.Geometry）？**
A：这类通用库通常面向"闭合多边形的整体膨胀/收缩"，返回结果可能包含多个不连通的子多边形（比如自交后分裂），而这里需要的是"保持为一条连续折线"的偏移结果（用于表示车道边界这种开放曲线），语义和通用库的多边形 buffer 操作不完全对应，且引入通用几何库的依赖对实时车载代码来说增加了不确定的性能开销，因此选择针对这个具体场景手写一个轻量的栈式算法。

## 3. 计算几何专题三：折线锐角切角算法（Chamfer）

**对应 PR**：07-14/07-15 restriction/box_collision 折线锐角修复

### 3.1 为什么需要切角

即使折线本身没有做偏移，一个**内角很小的顶点**（比如小于 90° 的右转急弯）本身也会给下游算法带来麻烦：
- `SmoothPolyline` 的 `LogSumExp` 光滑化在夹角很小的拐点附近，两条邻边的"归属区域"急剧变化，容易在数值上不稳定；
- `ShiftPolyline` 在这种尖角上做偏移时更容易触发上一节的翻转问题；
- 尖角本身也不符合真实世界道路边界"平滑过渡"的几何特征，属于采样/生成过程中的伪影。

**切角（Chamfer）** 是图形学/CAD 领域处理尖角的标准手法：把尖角"削平"，用一条短的斜边替代原来的顶点，使折线在拐角处变成"钝一些"的两个连续拐角，而不是一个极端尖锐的拐角。

### 3.2 算法步骤

1. **判定哪些顶点需要切角**：用向量叉积判断顶点是左转还是右转，用向量点积算出夹角的余弦值。**只对内角小于 90° 的右转顶点**做切角处理（左转顶点、钝角/平角顶点保持原样不变）——这是因为本项目里"右转锐角"对应的具体场景（比如车辆右前方 box_collision 边界贴近障碍物拐角）才是数值不稳定的高发地带，是针对性修复，不是无差别处理所有尖角。
2. **计算退让距离（leg）**：给定目标切角斜边长度 `base_length`，需要在两条邻边上各退让一段距离 `leg`，使得切出的斜边恰好等于 `base_length`。根据等腰三角形的几何关系：

$$
\text{leg} = \frac{0.5 \times \text{base\_length}}{\sin(\theta/2)}
$$

其中 $\theta$ 是顶点的内角。这个公式来源于：以顶点为顶角、两条腰长度为 `leg` 的等腰三角形，底边长度为 $2\cdot\text{leg}\cdot\sin(\theta/2)$，令其等于 `base_length` 反解即可。

3. **退让距离的钳制（clamp）与等比例缩放**：
   - 如果某一侧线段本身长度不足以支撑退让量 `leg`（比如线段本身很短），直接把 `leg` 钳制为该线段的长度。
   - 更复杂的情况：**相邻两个切角共享同一条线段**（比如折线上两个连续的尖角中间只隔一条短线段），此时两侧退让量之和可能超过这条共享线段的总长度，需要按比例整体缩小两侧的退让量，保证退让后不会在同一条线段上产生"退让区间重叠"这种非法结果。
4. **替换顶点**：用退让点算出的两个新点替代原顶点，折线从"经过一个尖角"变成"经过一条短斜边"。
5. **迭代收敛**：因为切出斜边后，斜边的两个新端点与其相邻的原顶点之间会形成新的夹角，这个新夹角**仍然可能是锐角**（尤其是连续多个尖角挨得很近时），所以整个切角过程需要**多轮迭代**（代码里设置最多 10 次），直到没有新的锐角产生为止（收敛）。
6. **去重合并**：多轮迭代后，可能产生彼此距离非常近的重复点（比如退让距离被钳制到极小时），需要对这些点做去重合并，避免下游算法处理零长度线段导致除零错误。

### 3.3 单测覆盖场景（复习清单）

- 单侧线段足够长 → 精确切出目标斜边长度；
- 单侧线段过短 → 退让量被钳制为线段长度；
- 非锐角/左转锐角 → 保持不变（验证判定逻辑的方向性）；
- 连续多个锐角 → 迭代收敛到无新锐角产生的稳定状态；
- 极短折线 → 不处理（避免在几乎退化的折线上做无意义的几何运算）；
- 相邻锐角共享短线段 → 按比例整体缩放退让量；
- 夹角趋近 0°（近似回折/U 型尖角） → $\sin(\theta/2)\to 0$，`leg` 公式分母趋零，需要特殊判断避免产生 NaN/Inf。

### 3.4 与几何工具库理论笔记的关系

`Clothoid.md` 第 7 章讲的 `SmoothPolyline`/`LogSumExp` 解决的是"**折线距离函数在拐点不可导**"的问题（数学连续性），而本节的 `ChamferAcuteAnglesOnPolyline` 解决的是"**折线本身在采样/生成阶段出现的伪影尖角**"问题（几何输入质量）——两者是互补关系：切角保证输入折线本身几何合理，`SmoothPolyline` 保证基于这条折线构造的距离场处处可导。即便输入折线已经切角处理过，`SmoothPolyline` 的可导性光滑化仍然是必需的（因为折线终归还是分段线性的，拐点处梯度理论上依然不连续，只是切角让拐点变"钝"、数值上更稳定，两者不能互相替代）。

## 4. 计算几何专题四：射线与直线求交的参数化解法

**对应 PR**：06-26 参考线起点前路径投影锚点缺失修复（`IntersectRayWithLine`）

### 4.1 参数化直线/射线表示

一条直线可以用"基准点 + 方向向量"参数化表示：给定基准点 $\bm p_0$ 和方向 $\hat{\bm d}$，直线上任意一点可以写成：

$$
\bm p(t) = \bm p_0 + t\hat{\bm d}, \quad t\in\mathbb{R}
$$

如果是**射线**（只能沿一个方向延伸），则限制 $t\ge0$。

### 4.2 两条直线（或一条射线+一条直线）求交

设直线 1：$\bm p_1(t) = \bm a_1 + t\hat{\bm d}_1$，直线 2：$\bm p_2(u) = \bm a_2 + u\hat{\bm d}_2$。求交点即求解方程组：

$$
\bm a_1 + t\hat{\bm d}_1 = \bm a_2 + u\hat{\bm d}_2
$$

这是一个关于 $(t,u)$ 的二元一次方程组（在二维平面里，$x,y$ 分量各给一个方程），用克莱姆法则求解：

$$
t = \frac{(\bm a_2-\bm a_1)\times\hat{\bm d}_2}{\hat{\bm d}_1\times\hat{\bm d}_2}, \qquad u = \frac{(\bm a_2-\bm a_1)\times\hat{\bm d}_1}{\hat{\bm d}_1\times\hat{\bm d}_2}
$$

（这里 $\times$ 表示二维向量叉积，标量形式：$\bm u\times\bm v = u_xv_y-u_yv_x$。）

- 如果分母 $\hat{\bm d}_1\times\hat{\bm d}_2 = 0$，说明两条直线**平行**（或重合），无唯一交点。
- 如果是"射线"（$t\ge0$ 或 $u\ge0$ 的约束），求出 $t,u$ 后还要检查是否满足非负性，若不满足说明交点落在射线的**反方向延长线**上，逻辑上不应采用。

### 4.3 IntersectRayWithLine 在本项目里的具体应用（06-26 PR）

- **基准点**：参考线 `min_s` 处的位置。
- **约束方向（对应上面的"直线2"）**：参考线在该处的**法线方向**（垂直于切线方向）——用于构造"参考线起点处的一条竖直分界线"。
- **射线方向（对应"直线1"）**：路径末端两个采样点的差向量方向（即路径在末端的切线方向，近似代表路径继续向后延伸应该走的方向）。
- **求交结果**：路径向后延伸这条射线，与参考线起点法线的交点，就是应该补插的"锚点"位置——它保证了补插点既落在参考线起点的横截面上（法线上任意一点到参考线起点的弧长投影都是 `min_s`），又大致延续了路径末端的走向趋势。

**PR3 修复的方向 bug**：射线方向应该是"路径向后延伸的方向"（即从后一个点指向前一个点，对应车辆继续后退的方向），但 PR1 里写反成了"从前一个点指向后一个点"（对应车辆前进方向），导致交点计算出来的位置南辕北辙——这是一个非常容易犯的、单纯"向量方向反了"的低级但隐蔽的 bug，提醒我们对每一个向量变量都要明确标注清楚"指向哪里""代表什么物理意义"，必要时在代码里加注释固化方向约定。

### 4.4 复习要点

这类"参数化直线求交"的写法在计算几何里极为常用（射线追踪、多边形裁剪、导航网格生成等场景都会用到），核心记忆点是：**用叉积代替除法/斜率计算交点参数**，天然避免了"垂直线斜率无穷大"这类特殊情况的额外分支判断，只需要在最后检查分母（叉积）是否为零即可统一处理"平行"这一种退化情况。

## 5. 计算几何专题五：曲率感知的圆弧外推

**对应 PR**：06-26 fallback 路径外推优化（PR2）

### 5.1 问题：为什么不能简单地"直线外推"

fallback（退路）路径需要在路径起点之前额外补出若干个点（用于后续投影、拼接等操作）。最简单的做法是"沿路径起点切线方向，等距离地往后延伸"（直线外推）。但如果路径本身在起点处有明显的曲率（比如车辆正在转弯中），直线外推出的延伸段会和路径实际的弯曲趋势"脱节"，造成路径在起点前后出现肉眼可见的"折角"，不符合路径应有的几何连续性。

### 5.2 圆弧外推公式推导

若已知路径起点处的位置 $\bm p_0$、切线方向 $\hat{\bm t}$、曲率 $\kappa$（$\kappa\ne0$），对应的**曲率半径**为 $r=1/|\kappa|$，圆心位于切线方向法线上距离 $r$ 处：

$$
\bm c = \bm p_0 + \text{sign}(\kappa)\cdot r\cdot\hat{\bm n}
$$

其中 $\hat{\bm n}$ 是切线 $\hat{\bm t}$ 逆时针旋转 90° 得到的法向量。

沿着这个圆弧向后（反方向）外推弧长 $\Delta s$，对应圆心角 $\Delta\theta = \Delta s / r$，外推点相对起点的位移量可以写成：

$$
\Delta\bm p = \hat{\bm n}\cdot r\cdot(1-\cos\Delta\theta) + \hat{\bm t}_{\text{backward}}\cdot r\cdot\sin\Delta\theta
$$

（这里 $\hat{\bm t}_{\text{backward}}=-\hat{\bm t}$ 是反向延伸方向。）

**推导直觉**：这本质上是"绕圆心旋转"的参数方程在局部坐标系（以切线方向、法线方向为轴）下的展开——沿圆弧移动角度 $\Delta\theta$ 后，切向位移分量是 $r\sin\Delta\theta$，法向位移分量是 $r(1-\cos\Delta\theta)$，这是圆的参数方程 $(\cos,\sin)$ 在小角度展开下的自然结果（$\Delta\theta\to0$ 时退化为直线外推：$\sin\Delta\theta\approx\Delta\theta$，$1-\cos\Delta\theta\approx0$）。

- **曲率趋近于零**（$|\kappa|<\epsilon$）：直接退化为直线外推（$\bm p = \bm p_0 - \Delta s\cdot\hat{\bm t}$），避免 $r=1/\kappa$ 在 $\kappa\to0$ 时发散。

### 5.3 与 Curve2d::CreateFromUniformPoints 的配合

外推出的点集要构造成一条新的 `Curve2d`，且这条曲线的**弧长参数化（s 坐标）**必须和车辆当前位置对齐——因为下游很多逻辑都依赖"曲线上某个 s 对应车辆走过的准确弧长"这个假设。因此外推段的起始弧长被设为 $s_0 = -\text{kNumBackwardPoints}\times s_{\text{step}}$（负数，表示在原路径起点"之前"），这样原路径起点对应的 s 恰好是 0，与车辆当前位置的弧长约定保持一致。

### 5.4 复习要点

这是"用局部曲率信息插值/外推曲线"的通用套路，思路可以类比机器人学中的 **Dubins 曲线/圆弧-直线混合路径**：只要知道某点的位置、朝向、曲率三个量，就能唯一确定一条圆弧，用它做局部外推/插值远比直接线性外推更符合实际运动学约束下的路径形态。

## 6. Frenet 投影专题：局部搜索 vs 全局搜索

**对应 PR**：06-29 FindSByPosition 替换 FindSByPositionLocally

### 6.1 问题的本质：在曲线上找"点到曲线的最近点投影"

给定曲线 $C(s)$（用弧长 $s$ 参数化）和一个查询点 $\bm p$，要找到 $s^* = \arg\min_s \|\bm p - C(s)\|$，这是几乎所有 Frenet 坐标转换的核心子问题。

### 6.2 局部搜索（FindSByPositionLocally）

**算法**：从一个初始猜测索引 `s_hint` 出发，每一步只比较"往前挪一格"和"往后挪一格"哪个更接近查询点，选择更近的方向继续挪动，直到两个方向都不能再改善为止（类似**爬山算法/坐标下降法**）。

- **优点**：如果 `s_hint` 已经在真实最近点附近，只需要 $O(\text{偏移距离})$ 步就能收敛，非常快。
- **致命缺陷**：这是一个**局部优化算法**，如果曲线不是"点到曲线距离关于 s 是单峰函数"（比如曲线自身有弯曲、S 形状），从一个远离真实最近点的 `s_hint` 出发做爬山搜索，**可能在中途遇到一个局部极小值就提前停止**，返回一个错误的、非全局最优的 $s$。

### 6.3 全局搜索（FindSByPosition）

**算法**：先对曲线上所有采样点做一次**线性扫描**（$O(n)$），找到欧氏距离最小的采样点索引，以这个索引为起点再做一次局部精化（比如在这个采样点附近做插值或再做一次局部爬山），确保收敛到真正的全局最近点。

- **优点**：不依赖任何初始猜测，**保证正确性**（在采样密度足够的前提下）。
- **代价**：$O(n)$ 的线性扫描，比局部搜索慢，但对于路径规划这种单帧只需要调用几次的场景，这个常数级的性能损失完全可以接受，正确性优先。

### 6.4 本项目两处 Bug 的共同规律

- `ReturnLastPath`：`s_hint` 固定为 `0.0`（曲线起点）；
- `GenerateReferencePathCurve`：`s_hint` 固定为 `curve.min_s()`（同样是曲线起点附近）。

**共同点**：两处都用了一个"看似合理但实际上是静态常量"的 hint 值，没有考虑到车辆实际位置可能已经远离这个 hint（车辆行驶到路径中段/末段，或者参考线存在弯曲导致车辆侧向偏移较大）。这是一类非常容易被忽视的 bug 模式：**"hint-based 优化"在 hint 失效的场景下会静默返回错误结果，而不是报错**，因此非常隐蔽——现象可能只是"规划路径偶尔抖动"或"覆盖范围判断错误"，很难第一时间联想到是投影函数返回了错误的 s。

### 6.5 工程权衡的一般性原则（面试常问）

> **什么场景该用局部搜索，什么场景该用全局搜索？**

- 如果能保证 hint **来自上一帧的准确结果**、且相邻帧之间目标位置变化很小（比如逐帧连续调用、增量式更新），局部搜索是安全且高效的选择（这也是很多实时系统采用局部搜索的原因——大部分调用场景下 hint 确实可靠）。
- 如果 hint 是**猜测值/常量/来自不同坐标系或不同曲线的移植值**，或者调用频率不高、对性能不敏感，应当优先选择全局搜索，用可预测的正确性换取略高的常数开销。
- 折中方案：先做一次**粗粒度的全局扫描**（比如按固定步长跳跃式采样，而非逐点扫描）定位到大致区间，再对该区间做局部精化，兼顾性能与鲁棒性——这也是 `FindSByPosition` 内部"先粗扫再局部精化"两阶段设计的思路。

## 7. C++ 内存安全专题：vector 头插、迭代器失效与均摊复杂度

**对应 PR**：05-06 GetProjectedSlSamples 性能与 coredump 修复

### 7.1 std::vector 的内存模型回顾

`std::vector` 在内存中是一段**连续存储**，当元素数量超过当前容量（capacity）时会触发**扩容**：分配一块更大的新内存（通常是当前容量的 1.5~2 倍，具体倍数取决于标准库实现），把所有旧元素**搬移**到新内存，然后释放旧内存。

### 7.2 为什么"头部插入"是 O(n)

`vector::insert(begin(), value)` 在头部插入一个元素时，即使不触发扩容，也必须把**所有已有元素整体向后搬移一位**（腾出头部位置），这个搬移操作本身就是 $O(n)$。如果在一个循环里做 $N$ 次头部插入，总复杂度是 $\sum_{i=1}^{N} O(i) = O(N^2)$——这正是 05-06 PR 修复前的性能问题根源。

### 7.3 为什么会导致野指针/迭代器失效引发 coredump

`vector` 扩容时会重新分配内存并搬移数据，这意味着：
- 所有指向旧内存的**迭代器**全部失效；
- 所有指向 vector 内部元素的**指针/引用**也全部失效（哪怲是指向"没有被移动位置"的元素，因为整块内存都换了，原来的地址不再有效）。

如果代码里有其他地方**持有了这个 vector 某个元素的指针或引用**（比如提前 `&vec[i]` 保存下来后续继续使用），一旦这个 vector 在中途发生扩容（哪怕只扩容一次），这些指针就变成了悬空指针（dangling pointer），后续访问会导致**未定义行为**——运气不好就是直接 coredump，运气"更差"则是不报错但读出脏数据，更难排查。

在 05-06 PR 的场景里，因为循环里反复插入触发**多次**扩容，指针失效的窗口被大大放大，是 coredump 频发的直接原因。

### 7.4 修复方案的两个关键技巧

1. **临时容器收集 + reserve 预分配**：先用 `reserve(num_behind_potential_samples)` 预分配好临时 vector 的容量，循环内用 `push_back` 追加——因为容量已经足够，`push_back` 不会触发扩容，均摊复杂度是 $O(1)$（严格来说，即使不 `reserve`，`push_back` 的均摊复杂度也是 $O(1)$，`reserve` 只是进一步保证"一次都不用扩容"，把最坏情况也压到最优）。
2. **反向迭代器一次性合并**：因为业务逻辑里是从近到远、逆向遍历生成的临时数据，直接用 `rbegin()/rend()` 把临时容器"反着"插入到目标 vector 头部，一次 `insert(begin(), rbegin(), rend())` 只需要**一次**内存搬移（把目标 vector 现有内容整体后移一次，腾出空间给临时容器的全部内容），无论临时容器多大，都只有一次 $O(n)$ 的搬移，而不是 $N$ 次。

### 7.5 均摊复杂度（Amortized Complexity）的严谨理解

`push_back` 单次操作最坏情况是 $O(n)$（触发扩容那一次），但如果扩容策略是"容量翻倍"，可以用**势能法（potential method）**证明：连续做 $N$ 次 `push_back`，总耗时是 $O(N)$，因此**均摊**到每次操作是 $O(1)$——这是"均摊分析"区别于"最坏情况分析"的经典例子，也是面试中常考的基础知识点。

### 7.6 复习清单式追问

- **Q：为什么扩容因子通常选 1.5~2 倍而不是每次只多加固定数量？** 因为固定增量会导致扩容次数是 $O(n)$ 次（等差数列），总搬移量是 $O(n^2)$；而倍增策略下扩容次数是 $O(\log n)$ 次，每次搬移量构成等比数列，总和是 $O(n)$——这是均摊复杂度分析的直接结论。
- **Q：`reserve` 和 `resize` 的区别？** `reserve` 只分配容量、不改变 `size()`、不构造元素；`resize` 会改变 `size()` 并构造/析构元素。本 PR 用 `reserve` 是因为只想预分配容量避免扩容，具体元素通过 `push_back` 逐个构造。

## 8. Coredump 排查方法论：从"链式清空"到"断言触发"

**对应 PR**：07-02 U-turn 参考线平滑器边界生成 coredump

### 8.1 这类 Bug 的典型特征

1. 代码里有一个**循环 + 条件校验 + 失败回退（pop_back/清空）**的模式：对每个采样点做有效性检查，一旦某个点校验失败，就把已经收集的结果**连带清空/回退**（"链式清空"）。
2. 清空之后，如果**下游逻辑没有对"结果为空/结果过少"做防御性判断**，直接把这个（几乎为空的）结果传给某个内部带 `CHECK`/`assert` 的函数（比如 `Curve2d::Create` 要求至少 2 个点才能构造一条曲线），就会在断言处直接 coredump。

用一句话概括这个 bug 模式：**"正常场景下很少触发的校验逻辑，在某个边界场景（这里是 U-turn 大曲率）下被批量误触发，导致中间结果被意外清空到低于下游断言要求的最小规模。"**

### 8.2 排查这类问题的通用步骤（可以直接用于面试的"讲一个你排查过的 coredump"问题）

1. **拿到 coredump 的调用栈**，定位到具体触发断言/CHECK 的那一行代码，明确断言的条件是什么（本例中是 `solution_points.size() >= 2` 之类的构造前置条件）。
2. **反推这个断言的输入是从哪里来的**，逐层往上追溯数据是如何被填充/清空的（本例中追溯到 `output.boundary` 在 `Compute` 函数循环中被 `pop_back` 链式清空）。
3. **定位清空逻辑的触发条件**，逐条分析每个校验条件在什么情况下会为 false（本例中是 `boundary_valid` 和 `center_line_valid` 两个几何有效性判断）。
4. **结合具体场景复现**，用仿真/可视化工具（这正是 04-17 PR 搭建的 mviz 可视化链路的用武之地）观察出问题的具体场景（U-turn 大曲率车道），确认是"正常路况的几何特征"误触发了"本该只用来过滤异常数据"的校验逻辑，而不是真的存在异常数据。
5. **设计针对性的短路修复**：不是删除或放宽校验条件（那样可能引入新的漏判风险），而是**为已知的"正常但容易误判"的场景类型（U-turn）单独加一个前置豁免判断**，让校验逻辑在遇到这类场景时直接跳过，保留其对真正异常场景的过滤能力。

### 8.3 "短路豁免"设计模式的适用边界（面试追问点）

**为什么不直接放宽 `boundary_valid`/`center_line_valid` 的判断阈值（比如把 60°~120° 改成更大范围）？**

因为阈值放宽是"全局生效"的，会削弱该校验对**其他真实异常场景**（比如地图数据错误导致的车道线抖动、噪声点）的过滤能力，属于"拆东墙补西墙"。而针对已知场景类型（`GetTurnType() == U_TURN`）做短路豁免，是**精确打击**——只对已确认为"正常几何特征、只是形状特殊"的场景放行，不影响其他场景下校验逻辑的正常工作，是更安全、更可维护的修复方式。这也是为什么两个 PR 都统一用 `lane_waypoint.lane->GetTurnType() == hdmap::Lane::U_TURN` 这个精确的语义判断，而不是简单调整数值阈值。

## 9. 障碍物决策转约束/代价的工程模式

**对应 PR**：04-24 障碍物约束与代价函数生成器

> 补充说明：`Clothoid.md` 第 6/8 章已经讲了 restriction/box_collision/obstacle 等各类 generator 的分类和数学公式，本节补充的是 04-24 PR **特有的双控制点绕行建模**这一工程模式细节。

### 9.1 为什么要同时约束"前角点"和"后轮中心"两个控制点

车辆状态里天然只有后轴中心的位姿 $(x,y,\theta)$，但车辆是一个有长宽的刚体：
- 如果只约束后轴中心，车辆过弯时**前角点可能会先于后轴中心"扫过"障碍物边缘**（外轮差现象），单点约束无法防止这种碰撞。
- 因此需要用 `PointTranslator`（详见 `Clothoid.md` 7.5 节）把约束/代价的作用点从后轴中心平移到车辆的前角点，前角点和后轮中心**分别**生成一套约束+代价，两者的雅可比都通过链式法则转换回对状态 $(x,y,\theta)$ 的导数，最终一起注入 iLQR 的同一个采样点。

### 9.2 绕行方向 → 侧向偏置的映射

上游决策模块只给出"左绕还是右绕"这样的**离散决策**，工程上需要把它转换成具体的连续几何量：

```
lateral_offset = +half_width  (若右绕，车辆右侧贴近障碍物左边缘)
lateral_offset = -half_width  (若左绕，车辆左侧贴近障碍物右边缘)
```

这个符号约定本身没有"唯一正确"的写法，重要的是团队内部要**统一约定**（比如始终以车辆朝向为参考系判断左右），并在代码注释/单测里明确验证，避免后续维护者混淆符号方向导致车辆"越绕越往障碍物钻"的严重 bug。

### 9.3 SamplePolylineWithHeadingCheck 的设计动机

障碍物多边形是一个**闭合的 CCW（逆时针）多边形**，理论上有多条边都可能是"离车辆最近的边"，但只有**车辆行驶方向上、朝向车辆一侧**的那部分边才是真正需要约束的（比如车辆从右侧绕行时，只需要关心障碍物左侧的边，不需要关心障碍物背面的边）。`SamplePolylineWithHeadingCheck` 通过检查候选边的法线方向是否与车辆行驶方向"合理夹角"来过滤，避免把不相关的障碍物边错误地纳入约束/代价计算，这也是节省计算量、避免"绕远路"式错误约束的关键一步。

### 9.4 硬约束 buffer 与软代价 buffer 分离设计

- `constraint_buffer`：约束（不可穿越边界）离障碍物实际边缘的安全距离，**必须严格保证**，通常设得较小（比如只需要保证物理不碰撞）。
- `cost_buffer + 决策附加 buffer`：代价（引导远离）的作用范围通常比约束buffer更大，让优化器在"物理上安全"的基础上，进一步倾向于离障碍物更远一些，提升舒适性和安全冗余。这种"约束管底线、代价管舒适"的分层设计，是本项目几乎所有 generator（restriction、box_collision、obstacle）的共同模式，也是第 `Clothoid.md` 8.3 节里"硬约束+软代价"分层思想在具体场景下的复用。

## 10. 可视化调试工程实践（mviz）

**对应 PR**：04-17、04-29、05-07、05-20

> 这部分是纯工程实践类知识，6 篇理论笔记完全没有涉及，但在面试中"如何debug复杂系统"这类问题里非常有价值。

### 10.1 可视化调试的分层设计模式

从 04-17 PR 可以提炼出一套通用的"调试可视化基础设施"分层模式：

```
数据层：Debug Proto（ClothoidPathOptimizerDebug）
   ↓ 记录算法运行时的中间状态（约束/代价/求解器耗时等）
传输层：PlannedResult 消息（跨进程/跨模块传递 debug 数据）
   ↓
渲染层：Producer（3D场景）+ ChartProducer（2D折线图）
   ↓ 从 debug proto 反序列化并转换成可视化图元
展示层：mviz 平台（Widget/图层/菜单树）
```

这种分层的好处是：**业务算法代码只需要负责"把中间状态写入 debug proto"这一件事**（`ClothoidPathOptimizerDebugger` 的职责），不需要关心具体怎么渲染、渲染成什么颜色/形状，渲染逻辑完全在独立的 Producer 里维护，两者通过 proto 这个"契约"解耦——这是一种典型的**关注点分离（Separation of Concerns）**实践。

### 10.2 决策过程可解释性设计（05-07 PR 的核心价值）

05-07 PR 把 `FeasibilityCheck` 的内部临时变量（原来创建即丢弃的 `status` 淘汰原因）改造成**输出参数**，这个改动背后的工程原则是：

> **任何做"多选一"或"筛选/淘汰"决策的模块，都应该在接口设计时预留"记录决策依据"的输出通道，而不是只返回最终结果。**

否则一旦最终结果不符合预期（比如车辆在路口选了一条"看起来不是最优"的轨迹），开发者除了里外翻查代码猜测原因外，没有任何直接线索——这类"决策留痕"设计在推荐系统、搜索排序、规则引擎等其他领域的可解释性建设中也是通用思路。

### 10.3 UI 状态降级兼容设计（04-29 PR）

Widget 滑块原本假设"折线索引一定非空"，当这个假设在新场景（只有路径点、没有折线索引）下不成立时，直接的处理方式是"禁用滑块"（用户体验差）或者"崩溃/报错"（更差）。04-29 PR 采用的是**优雅降级（graceful degradation）**：用一个合理的默认行为（用三条路径长度的最大值作为滑块上限）替代原本依赖的数据源，同时调整显示文案让用户明确知道当前处于哪种模式（"Polyline Index" vs "Path Point"）。这是 UI 工程里处理"数据源缺失/变化"的标准套路。

## 11. 数值稳定性通用套路总结

贯穿多个 PR（04-24 障碍物精度处理、07-14/07-15 折线偏移与切角、06-26 除零风险）的数值稳定性处理，可以总结成几条可复用的通用原则：

1. **除法前检查分母是否趋近于零**：无论是 $\sin(\theta/2)$（切角公式）、叉积（求交平行判断）、还是曲率 $\kappa$（圆弧外推），只要公式里出现除法，几乎总要先判断分母是否在数值容差范围内退化为零，退化时切换到极限情况下的等价简化公式（比如切角不处理、求交返回 none、外推退化为直线）。
2. **对"退让/偏移"类操作做钳制（clamp）**：任何"从某个基准点向外扩展/退让一段距离"的操作，都要检查可用空间是否充足，不足时钳制到边界值，而不是任由计算结果超出合理范围产生非法的几何形状。
3. **迭代类算法要设置最大迭代次数上限**：切角的多轮迭代、AL 外层循环、iLQR 内层循环，都设置了 `max_iterations` 类的硬上限，防止因为收敛判断的边界条件问题导致死循环。
4. **对涉及浮点比较的地方使用 epsilon 容差而非精确相等**：几何算法里"两点是否重合""两条线是否平行"这类判断，永远用 `< kEpsilon` 而不是 `== 0`。
5. **单测要覆盖"退化情况"而非只覆盖"正常情况"**：本文提到的所有 PR 单测清单里，都能看到"共线""夹角趋近 0°""极短折线"这类专门针对退化边界的用例，这是保证数值稳定性修复真正生效、且未来不会被回归破坏的关键手段。
