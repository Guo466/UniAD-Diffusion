## 1. 项目背景总览

**ClothoidPathOptimizer（回旋曲线路径优化器）** 是 Walle 自动驾驶系统 Planning 模块的核心路径规划算法，负责在给定参考线、车道边界、障碍物决策、限制区域等约束条件下，生成一条曲率连续（Clothoid，即回旋曲线）、满足车辆运动学约束、代价最优的行驶路径。

其技术底座是一套基于 **iLQR（Iterative Linear Quadratic Regulator）+ AL（Augmented Lagrangian，增广拉格朗日）** 的轨迹优化求解器（类似学术界的 ALTRO 求解器思路）：

- **状态/控制建模**：以路径弧长为自变量，状态量包含位置、朝向、曲率等（`ClothoidPathStateIndex`），控制量为曲率变化率等（`ClothoidPathControlIndex`）。
- **动力学离散化**：通过 `DiscretizedModel` + RK4/Forward Euler 积分器（`integrator.h`）将连续动力学离散为逐步（stage-wise）状态转移。
- **可行轨迹初始化**：`FeasibleTrajectoryGenerator` 基于 infeasible-start 模型生成满足动力学的初始可行解，供后续优化收敛。
- **约束与代价体系**：车道边界（lane boundary）、限制区域（restriction）、碰撞盒边界（box collision）、障碍物绕行（obstacle decision）、斥力场（repulsion）、引导线（guide line）等，均被转化为 `InequalityConstraint`（硬约束）和 `CostFunction`（软代价），逐 stage 注入求解器（`ConstraintAndCostSet`）。
- **AL 外层 + iLQR 内层求解**：`ALSolver` 负责外层对偶变量与惩罚系数更新（`ConstraintPenalty`），`Solver`（iLQR）负责内层反向传播（backward pass，含正则化与 Cholesky 分解保证数值稳定）+ 前向传播（forward pass，含线搜索）求解每次迭代的最优轨迹增量。
- **调试与可视化**：`ClothoidPathOptimizerDebugger` 将求解全过程（参考路径、初始路径、最优路径、各类约束/代价、求解器耗时与状态）写入 debug proto，供 `mviz`（内部可视化平台）实时渲染。

在实习期间，我的工作横跨该项目的 **可视化调试工具链建设** → **核心算法功能开发（障碍物约束代价）** → **性能与数值稳定性问题修复** → **几何算法健壮性重构** 四个阶段，覆盖了从"看得见"到"跑得对"到"跑得稳"的完整工程闭环。

### 3.2 【04-24】障碍物约束与代价函数生成器（核心算法开发）

**背景**：上游决策模块会输出障碍物绕行方向（`ObstacleDecision`：左绕/右绕），需要将这一决策转化为 iLQR 求解器可用的数学约束和代价。

**核心实现**（`ObstacleConstraintAndCostGenerator`）：
1. 对每个障碍物多边形先做 **Douglas-Peucker 抽稀**（精度 0.05m）降低计算量。
2. 对轨迹每个采样点，针对车辆**前角点**和**后轮中心**两个控制点分别生成约束+代价：
   - 按绕行方向确定侧向偏置 `lateral_offset = ±half_width`；
   - 用 `PointTranslator` 把车辆位姿平移到对应角点坐标系；
   - `SamplePolylineWithHeadingCheck` 按行驶方向从 CCW 障碍物多边形中选取靠近车辆的一条边；
   - 用 `constraint_buffer`（硬约束）和 `cost_buffer + 决策附加 buffer`（软代价）对该边偏移，生成最终约束/代价多边形。
3. 约束用 `CornerSmoothPolylineConstraint`/`RearWheelSmoothPolylineConstraint`（不可穿越），代价用对应的 `SmoothPolylineCostFunction`（软性引导远离）。
4. 数据结构扩展：`ObstacleDecision` 加入 `DecisionInput`；`ConstraintAndCostSet` 新增障碍物约束/代价字段；proto 新增配置项（buffer/weight/sample_distance）与 debug 字段。
5. 编写 293 行单测：验证约束/代价数量对齐、代价数值与手工计算完全一致。

**涉及知识**：Douglas-Peucker 多边形简化算法、计算几何（CCW 多边形、线段偏移采样）、坐标系变换、iLQR 约束/代价接口设计、单元测试驱动的数值验证。

### 3.4 【05-06】GetProjectedSlSamples 性能与 coredump 修复

**背景**：`GetProjectedSlSamples` 需要将车辆当前位置之后（behind）的若干采样点前插到 `monotonic_s_samples`/`l_samples`/`point_samples` 三个 vector 头部。

**根因**：原实现在循环中逐次调用 `insert(begin(), ...)`：
- 单次头部插入是 O(n)（需整体右移），循环 N 次总复杂度 **O(N²)**；
- `insert` 可能触发扩容（realloc），导致已持有的迭代器/指针失效 → 在多处引用该指针的场景下引发 **coredump**。

**修复**：
1. 预先声明并 `reserve` 三个临时 vector；
2. 循环体内改为 `push_back` 追加（均摊 O(1)）；
3. 循环结束后利用**反向迭代器**（`rbegin()/rend()`）一次性批量插入回原 vector 头部——因采样本身是从近到远逆向遍历的，反向迭代器天然纠正为正序，无需额外 `reverse`。

**效果**：时间复杂度从 O(N²) 降至 O(N)，原 vector 最多扩容一次，消除指针失效风险，根治 coredump。

**涉及知识**：`std::vector` 内存模型与扩容机制、迭代器失效、均摊复杂度分析、反向迭代器技巧。

### 3.6 【06-26】参考线起点前路径投影锚点缺失修复（3 个递进 PR）

**背景**：`GenerateProjectedFrenetCurve` 需要把路径曲线投影到参考线 Frenet 坐标系。当路径起点在参考线起点（min_s）之前时（典型场景：fallback 退路、车辆接近参考线起点），逆向追溯采样点会落到参考线有效范围外，导致投影起始段缺失合理锚点，Frenet 曲线在起点处**不连续/方向跳变**。

**PR1（核心算法）**：新增 `IntersectRayWithLine`：以参考线 min_s 处位置为基准点、切线方向为约束方向构造参考线起点法线，以路径末端两采样点差向量为射线方向，求解射线与法线交点（平行或反向则返回 none）；当采样点跑到 `min_s` 之前且开启 `force_insert_point_before_start_s` 时，用交点作为补插锚点（l 值投影后 clamp）插入。同时将 `sampling_start_path_s` 从 `base::none` 改为车辆当前弧长 `s_on_path`，确保回溯起点准确。

**PR2（fallback 曲率感知外推）**：`GenerateFallbackPath` 原来在终点前**等距**外推，改为**曲率感知圆弧外推**：曲率趋零则直线外推，否则按圆弧公式 `pos + normal * r * (1 - cosΔθ) + backward_dir * r * sinΔθ` 推算，使外推段与路径曲率几何一致；强制车辆位置插入路径；`Curve2d::Create` 改为 `Curve2d::CreateFromUniformPoints`（以 `s0 = -kNumBackwardPoints * s_step` 对齐车辆位置的 s 参数化）。同时对求交失败场景补充兜底（用参考线 min_s 处点 + l=0 作为默认锚点）。

**PR3（修正射线方向 bug）**：PR1 中射线方向写反（用了 `p1-p0` 而非 `p0-p1`），修正为路径向后延伸方向（对应车辆行驶反方向），交点才能正确落在参考线起点附近。

**涉及知识**：射线-直线求交的参数化方程解法、圆弧几何外推、Frenet 坐标系与曲线参数化（arc-length parameterization）、边界场景兜底设计、渐进式 bug 定位与递进修复。

### 3.7 【06-29】全局搜索替换局部搜索修复投影错误

**根本差异**：
- `FindSByPositionLocally(point, s_hint, ...)`：**局部爬山搜索**，从 hint 索引出发每步只扩展一格，O(偏移距离)，但依赖 hint 必须在真实最近点附近，否则陷入局部极小值。
- `FindSByPosition(point, ...)`：**全局遍历搜索**，先线性扫描找全局最近邻再局部精化，O(n) 但结果正确性有保障。

**两处 Bug**：
- **ReturnLastPath**：hint 固定为 `0.0`（路径起点），车辆行驶到路径中/末段时局部爬山停在错误局部极值，导致 `sampling_start_s` 偏差、fallback 路径起始段错位，引发规划抖动或 coredump。
- **GenerateReferencePathCurve**：hint 固定为 `curve.min_s()`，当参考路径弯曲或车辆侧向偏移大时局部搜索误收敛，导致覆盖范围判断（`s >= min_s && s+path_length_ < max_s`）失误，误判触发不必要的路径延伸/跳过。

**修复**：两处均替换为 `FindSByPosition`，用全局扫描消除对初始 hint 的依赖。

**涉及知识**：局部搜索 vs 全局搜索的复杂度与正确性权衡、Frenet 投影算法、hint-based 优化的失效场景分析。

### 3.8 【07-02】U-turn 场景参考线平滑器边界生成 coredump 修复

**背景**：`ReferenceLineSmootherBoundaryGenerator::Compute` 以 1m 步长采样，对每点做两项有效性检查，任一失败触发 `pop_back` 链式回退清空 `output.boundary`，最终 `solution_points.size() == 1` 时传入 `Curve2d::Create` 触发**断言 coredump**。

**根因（两个 Bug）**：
1. `center_line_valid` 误判：U-turn 车道大曲率弯折处 `last→current→next` 三点向量内积为负，`IsReverse` 误判为方向反折，正常弯道点被过滤。
2. `boundary_valid` 误判：U-turn 弯折最深处前后横截面夹角超过 60°（`has_large_heading_diff=true`），触发相交检测，两线段确实相交 → `boundary_valid=false`，同样链式清空。

**修复**：两处检查前均增加 U-turn 类型短路判断（`lane_waypoint.lane->GetTurnType() == hdmap::Lane::U_TURN`），是 U-turn 则跳过对应检查、直接视为有效。两个 PR 共用统一判断方式（第二个 PR 同步修正第一个 PR 中 `IsUturnLane()` 接口调用方式的变更）。

**涉及知识**：断言/CHECK 引发的 coredump 排查、几何有效性检查算法（线段相交判断、方向反折判断）、场景化短路设计（避免"一刀切"检查误伤正常大曲率场景）。

### 3.9 【07-14~07-15】折线几何处理健壮性重构（ShiftPolyline + 锐角切角）

**背景**：`clothoid_path_optimizer` 中车道边界、restriction、box_collision 等约束/代价均依赖对折线（polyline）做几何变换与采样，核心工具函数是 `ShiftPolyline`（整体法向平移）与 `BuildAndSimplifyBoxCollisionPolyline`/`BuildAndSimplifyRestrictionPolyline`（采样生成 + Douglas-Peucker 抽稀）。两个 PR 是同一复现分支下连续排查折线在**尖锐拐角处几何处理不健壮**问题的产物。

**问题一：ShiftPolyline 偏移超限时线段翻转自交**

- **根因**：原实现对每个顶点独立用"角平分线方向+偏移量"计算偏移位置；当拐角很尖锐且偏移距离较大时，某段偏移量超过原始线段长度临界值，导致该线段偏移后**方向翻转**（起点落在终点之后）。原实现检测到超限后直接放弃整体平移、返回原始折线，导致该本该生成的偏移边界整体失效（仿真表现为偏移折线与原折线完全重合）。
- **修复**：重写为**基于偏移射线 + 栈式回退合并**的经典算法：为每条原线段计算"沿法向偏移后的射线"（`DirectedLine`），用栈 `kept_segments` 顺序处理——新射线与栈顶射线求交点，若交点相对栈顶线段方向发生翻转，说明栈顶线段已被"吃掉"，弹出继续向前求交，直至找到不翻转的交点或栈为空，再压入当前线段；最终折线由栈中线段交点+末段终点组成。可正确处理单个及连续多个尖锐拐角在大偏移量下相继被"吞并"的级联情况。
- **单测覆盖**：单拐角翻转退化为交点、连续多拐角级联收敛、偏移小于临界值时行为不变、共线/近似共线夹角趋近 0° 时不产生 NaN/Inf。

**问题二：restriction/box_collision 折线右转锐角**

- **根因**：参考线曲率变化大或障碍物边缘不规则路段，采样得到的折线出现局部内角很小的右转锐角，给下游 `ShiftPolyline` 偏移、约束/代价采样带来数值不稳定，仿真表现为 box_collision 边界在障碍物边缘走向异常。
- **修复**：新增通用函数 `ChamferAcuteAnglesOnPolyline`（锐角切角），在两处折线生成入口（先于 Douglas-Peucker 抽稀）调用：
  1. 仅对内角 < 90° 的**右转**顶点做切角（叉积判转向、点积算夹角余弦），左转/钝角/平角不变；
  2. 按 `leg = 0.5 × base_length / sin(夹角/2)` 计算两侧退让距离，使切出斜边长度精确等于目标值；
  3. 当两侧线段长度不足支撑退让量时**钳制**为线段长度本身（相邻切角共享同一线段、退让量之和超过线段一半时按比例整体缩放），避免非法折线；
  4. 用两个新点替换原顶点；因连续锐角切角可能产生新锐角，最多迭代 10 次直至收敛；最后对距离过近的重复点去重合并。
- **单测覆盖**：单侧线段足够/过短（钳制）、非锐角/左转锐角不变、连续多锐角迭代收敛、极短折线不处理、相邻锐角共享短线段按比例缩放、夹角趋近 0° 时不产生 NaN/Inf。

**评测**：两 PR 均在闭环仿真复现分支验证；General 全量回归比对，个别 diff case 经核实均与本次改动无关（未调用 ClothoidPathOptimizer 或仿真自身问题），最终结论均为 **no diff，评测通过**。

**涉及知识**：计算几何（角平分线偏移的局限性、射线-射线求交、栈式几何处理算法）、数值稳定性（钳制/等比例缩放避免非法输出、NaN/Inf 边界防护）、迭代收敛设计、仿真回归验证方法论。

## 4. 与 ClothoidPathOptimizer 项目的联系总结

这十个 PR 并非孤立的任务，而是沿着 ClothoidPathOptimizer **"能看见 → 能算对 → 能算稳 → 能算得健壮"** 的工程成熟度曲线逐步推进的，可以映射到该项目的技术分层：

```
┌─────────────────────────────────────────────────────────────┐
│  可视化调试层 (mviz)                                          │
│  04-17 Producer/Chart搭建 → 04-29 车辆轮廓 → 05-07/05-20 路口 │
│  → 贯穿所有后续PR：每次算法修复都依赖这层做问题定位与效果验证    │
├─────────────────────────────────────────────────────────────┤
│  约束/代价生成层 (ConstraintAndCostSet)                       │
│  04-24 障碍物约束代价生成器（新增一整类 Decision→约束/代价映射）  │
│  07-14/07-15 底层折线几何工具（服务于lane boundary/restriction │
│  /box_collision等所有约束代价的折线预处理）                     │
├─────────────────────────────────────────────────────────────┤
│  几何与Frenet投影层 (frenet_path / curve2d)                    │
│  06-26 射线求交补锚点 → 06-29 全局搜索替换局部搜索              │
│  两者都是 ClothoidPathOptimizer 与参考线/上一帧路径对接的        │
│  核心投影环节，直接决定优化器初始状态与fallback的正确性          │
├─────────────────────────────────────────────────────────────┤
│  求解器输入前置（参考线生成，非ClothoidPathOptimizer本体但为其  │
│  提供输入）                                                    │
│  07-02 U-turn参考线边界coredump —— 保证极端曲率场景下           │
│  ClothoidPathOptimizer仍能拿到合法的path_boundary输入           │
├─────────────────────────────────────────────────────────────┤
│  性能与内存安全 (跨层)                                          │
│  05-06 vector头插O(N²)+野指针 —— 保障Frenet投影环节的实时性     │
│  与内存安全，是所有上层功能正确运行的前提                        │
└─────────────────────────────────────────────────────────────┘
```

**技术脉络串联**：

1. **先建立可观测性，再动手改算法**：04-17 建立的 mviz 可视化基础设施，是后续所有 bug（05-06 的 coredump、06-26 的路径跳变、07-02 的 U-turn 断言、07-14/15 的折线自交）能够被**发现、复现、验证修复效果**的前提工具。这也是我在算法工程中学到的重要方法论——"没有可视化就没有可调试性"。

2. **从"功能实现"到"边界健壮性"的递进**：04-24 的障碍物约束代价生成器是在**理想输入**下让 ClothoidPathOptimizer 具备绕障能力；而 06-26/06-29/07-02/07-14-15 则是逐步发现并修复在各种**边界/极端场景**（车辆偏离参考线起点、大曲率 U-turn、尖锐拐角折线）下算法失效的问题。这正体现了工业级优化算法从"跑通 demo"到"车规级可靠"所必须经历的健壮性打磨过程。

3. **底层几何工具的复用性**：`ShiftPolyline`、`ChamferAcuteAnglesOnPolyline`、`IntersectRayWithLine`、`FindSByPosition` 这些看似独立的几何工具函数，实际上被 lane boundary、restriction、box_collision、obstacle 等**几乎所有约束/代价生成器**共享调用。因此 07-14/07-15 对折线几何底层算法的重构，其影响面覆盖了整个 ClothoidPathOptimizer 的约束体系，是"四两拨千斤"式的关键修复。

4. **与 iLQR/AL 求解器的接口关系**：04-24 新增的障碍物约束/代价最终都是通过 `CollectConstraintsAtSample`/`CollectCostsAtSample` 逐 stage 注入 `ConstrainedProblem`，交由 `ALSolver` 的外层对偶更新 + `Solver`（iLQR）内层反向/前向传播求解；06-26/06-29 修复的 Frenet 投影问题直接决定了 `GenerateInitialPaths` 产出的初始猜测轨迹是否合理，进而影响 iLQR 迭代的收敛速度和最终解的质量——错误的初值可能导致求解器多花几轮迭代甚至不收敛回退到 fallback。
